# ADR-009: The output alphabet is entries plus composition, not a tuple table

Status: **accepted**. Closes open design question 02. Audit: "What converged",
the render map bullet.

## Context

`data/render/ipa.yaml` held one row per feature tuple the model can produce:
86 consonants keyed `letter|geminate|emphatic|nasal`, 10 vowels keyed
`quality|long|emphatic`, 2 nasals, 1 release. 99 rows, generated by
`tools/build_render_map.py`.

The design was deliberate and its benefit was real: a tuple with no row raises
`NotationError`, so an unrenderable sound is loud rather than silent. The
question was whether that benefit survives a schema whose row count is not the
product of the feature space.

It does not need to. The row count was never the guarantee — coverage was, and
the row count was one way to get it.

### Why the row count was the problem

The file did not say what a feature *means*; it said what every combination of
features *spells*. Gemination is one fact, say the consonant twice, written 28
times as `bb`, `tt`, `θθ`. Consequences: adding a letter was two rows minimum,
adding a feature doubled the file, and a second notation was a second 99-row
generated file with the same redundancy. Because nobody would write 99 rows by
hand, the generator existed; because the generator existed, the committed data
file was a build artefact and the real source was Python.

## What was audited first

**1. Which of the 99 rows are not a composition.** None of them.
`build_render_map._consonant` composed every token from three tables: `BASE`
(30 letters), `EMPHATIC` (2 — raa, lam), `NASALIZED` (4 — noon, meem, waw,
yaa). Nasal overrode outright and was never doubled; otherwise emphatic-or-
plain, doubled if geminate. Vowels were `VOWEL[q] + "ˤ"? + ":"?`. So the
genuine content was 37 entries and three rules, and the other 62 rows were
their product.

**2. Whether `NasalPlace` and `ReleaseKind` are in the tuple space.** Yes, as
their own tables — `nasals` keyed on `place|emphatic`, `releases` on `kind`.
They are unchanged by this decision; only their key type is now the enum.

**3. Whether a second notation is actually wanted.** Not established. The
design document cited "the mualem spec in `docs/`" as the reason to think so;
no such document exists in the tree. `docs/README.md` links to
`docs/mualem_conversion.md`, which is not present either.

This did **not** close the question as "no change": the redundancy above
justifies the decision on its own, and a second notation is now a ~37-entry
hand-written file rather than a second generator. But the decision is not
recorded as being made for a second notation, because nothing yet requires one.

**The 28 rows unreached over the corpus were not pruned.** Reach is not
evidence of deadness — some are reachable only under a non-default khilaf, and
the khilaf catalogue is incomplete (see design question 06). They stopped
being rows; the overrides that produce them remain. Three reviewers
independently measured 71/99 and two proposed deleting the remainder; that
would have been wrong.

## Decision

One entry per letter, quality, nasal place and release kind. An entry is a
bare token, or a map with `plain` and whichever of `emphatic` and `nasal` the
letter admits. `render/alphabet.py` composes: geminate doubles, long appends
`:`, nasal takes the entry's nasal token and is not doubled — a held nasal is
already the sound of a doubled letter.

`schema_version: 2`. `tools/build_render_map.py` is deleted. The file's claim
to be the only one in the package holding a phoneme string is now true; it was
false while the generator held every token.

### Totality, restated

The guarantee is no longer "every tuple has a row". It is two claims, and both
are checked:

1. **Coverage, at load.** The four tables are exact against `CanonLetter`,
   `Quality`, `NasalPlace` and `ReleaseKind` — in both directions, so a member
   with no entry and an entry naming no member are equally errors. Adding a
   letter to the model is one entry here, and forgetting it fails at load
   rather than on the verse that first needs it.
2. **No suffix rule for a feature an entry does not offer.** Nine letters
   carry an `emphatic` token — the seven of istilaa plus the raa and the
   divine lam — which is exactly the set `rules/tafkheem.py` can recolour
   (`always_heavy | CONDITIONAL`). The other 21 have no entry for it and
   raise. `tests/test_render_map.py` asserts the two sets are equal, so the
   alphabet and the rule cannot drift apart.

Claim 2 is the one that carries the original benefit. A generic "emphasis
appends ˤ" rule would have answered `bˤ` for a tuple the model cannot produce
and made `NotationError` unreachable — which is precisely what the generator's
`HEAVY_CAPABLE` frozenset was guarding. The same applies to the four letters
that take a nasal and no emphasis: emphasis is checked before the nasal
branch, or the nasal token would answer and drop the feature silently.

## Rejected: keep the table, generate it from a semantic source

The YAML stays as it is and the semantic entries become the generator's input.
Cheaper and lower risk, and totality would be unchanged. Rejected because the
committed data file is then explicitly a build artefact, which the package has
otherwise avoided, and because a second notation still costs a second
generated file — so the redundancy is moved rather than removed.

## Evidence

The change is token-for-token identical. All 261 tuples in the full
cross-product were resolved against the old map and the new resolver: the same
99 resolve to the same tokens, and the same 162 raise. The two parity gates
render every word of the Quran in both scripts through this path; neither
moved, and no floor moved.

The identity check found one defect before it landed — the nasal branch
answering for a letter that takes no emphasis — which is the reason the check
was run before the resolver was written rather than after.
